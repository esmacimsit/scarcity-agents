# Fine-Tune Plan

This document defines the fine-tuning plan for the AI Society project.

The purpose of the fine-tuning phase is not to train a general chatbot. The purpose is to test whether social and economic behavior norms can be internalized into an LLM-based agent decision policy.

The fine-tuned policy will be compared against the existing baselines:

- random policy
- rule-based policy
- zero-shot LLM policies
- few-shot LLM policies

---

## 1. Research Goal

The project studies a scarcity-based artificial economy where agents repeatedly choose between two actions:

```text
gather → produce food
work   → produce coin
```

The environment is kept fixed. The agent state representation is kept fixed. The main variable is the decision policy.

The fine-tuning phase asks:

> Can separate lightweight LoRA adapters internalize different economic behavior norms, so that the same base LLM can produce different society-level outcomes depending on the trained adapter?

In other words, fine-tuning is treated as a behavioral intervention in an artificial society.

---

## 2. Fine-Tuning Method

This project will not use full model fine-tuning.

The target method is:

```text
MLX LoRA / QLoRA-style adapter training on Apple Silicon
```

The base model will remain unchanged. Three small LoRA adapters will be trained on synthetic decision examples, one for each economic behavior regime.

The expected structure is:

```text
base model + survival LoRA adapter → survival-oriented action decision
base model + social welfare LoRA adapter → society-aware action decision
base model + wealth LoRA adapter → self-interested action decision
```

This is safer and more practical than full fine-tuning because:

- the base model is not overwritten
- training is lighter
- adapter outputs can be tested independently
-- the project can fall back to the existing zero-shot and few-shot results if training is not useful

The primary plan is to train three separate adapters rather than one shared adapter. This makes the behavioral regimes easier to separate and allows each adapter to use its own best checkpoint.

## 3. Behavior Regimes

The fine-tuned model should support the same three behavior regimes used in the zero-shot and few-shot experiments.

| Daily Name | Academic / Policy Name | Goal |
|---|---|---|
| Orta | `survival` | Protect the agent's own long-term survival. |
| İyi | `social_welfare` | Survive while reducing society-level scarcity, deaths, and inequality. |
| Selfish | `wealth_maximizing` | Prioritize increasing the agent's own wealth. |

The corresponding fine-tuned policies will be:

```text
llm_survival_finetuned
llm_social_welfare_finetuned
llm_wealth_maximizing_finetuned
```

---

## 4. Three Separate LoRA Adapters

The first fine-tuning attempt will use three separate LoRA adapters, not one shared adapter.

The adapters will be:

```text
survival_adapter
social_welfare_adapter
wealth_maximizing_adapter
```

The corresponding simulation policies will be:

```text
llm_survival_finetuned
llm_social_welfare_finetuned
llm_wealth_maximizing_finetuned
```

This design treats each adapter as a learned economic behavior regime.

The research question becomes:

> If different economic norms are trained into separate LoRA adapters on the same base model, how much do the resulting society-level outcomes change?

This is more suitable for this project than a single shared adapter because each behavior regime may have a different training sweet spot.

For example:

```text
social welfare may learn quickly and stabilize after fewer epochs
survival may need more training to learn balanced behavior
wealth maximizing may overfit quickly and may need early stopping
```

Using separate adapters allows each regime to keep its best checkpoint instead of forcing one shared checkpoint for all objectives.

A single objective-conditioned adapter remains a fallback option if separate adapter training becomes too costly or difficult.

## 5. Dataset Strategy

The dataset will be synthetic and hybrid.

Hybrid means examples will come from multiple controlled sources:

| Source | Meaning |
|---|---|
| `rule_generated` | Deterministic survival and scarcity guardrails. |
| `handcrafted_objective` | Manually designed objective-specific examples. |
| `few_shot_guided` | Behavior patterns derived from the few-shot experiment results. |
| `teacher_guided` | Decisions generated by a stronger teacher model and filtered by regime-specific validators. |

The goal is not to copy one policy exactly. The goal is to teach stable regime-specific tendencies.

Because the primary plan uses three separate adapters, the dataset will be split by behavior regime:

```text
data/finetune/survival/
data/finetune/social_welfare/
data/finetune/wealth_maximizing/
```

Each regime can have its own train/validation split, label balance, and best checkpoint.

### Teacher-Guided Examples

The hybrid dataset may also include teacher-guided examples.

A stronger local model, such as Qwen 14B, can be used as a teacher model to label additional state/action examples. The smaller target model or adapter can then learn from these examples during LoRA training.

This is similar to a lightweight distillation-style dataset generation process:

```text
larger teacher model → objective-conditioned action labels → smaller fine-tuned adapter
```

Teacher outputs will not be accepted blindly. They must be filtered by regime-specific validation rules so that the intended behavior regime is preserved.

Examples:

```text
social_welfare + high scarcity + high price → teacher should choose gather
wealth_maximizing + food safe + coin low → teacher should usually choose work
wealth_maximizing + food critical → teacher should choose gather
survival + food safe + scarcity low + coin low → teacher may choose work
```

This adds nuance while keeping the dataset aligned with the intended economic behavior regime.

## 6. Training Example Schema

A raw decision example should contain the target behavior regime, state, action, and source:

```json
{
  "regime": "social_welfare",
  "state": {
    "timestep": 10,
    "food": 3.0,
    "coin": 5.0,
    "productivity": 1.1,
    "wealth": 12.0,
    "food_price": 6.0,
    "alive_count": 30,
    "dead_total": 20,
    "total_food": 120.0,
    "scarcity_ratio": 2.1
  },
  "action": "gather",
  "source": "handcrafted_objective"
}
```

The model-facing prompt/completion format should be simple:

```json
{
  "prompt": "Behavior regime: social_welfare\nState:\nfood: 3.0\ncoin: 5.0\nfood_price: 6.0\nscarcity_ratio: 2.1\nalive_count: 30\ndead_total: 20\nChoose one action: gather or work.\nReturn exactly one word.",
  "completion": "gather"
}
```

The completion must be exactly one of:

```text
gather
work
```

## 7. Labeling Rules

### 7.1 Survival / Balanced Objective

The survival objective should represent a balanced agent.

Expected behavior:

```text
food low → gather
food price high → gather
scarcity high → gather bias
food safe + coin low → work
otherwise balanced
```

This policy should not be fully altruistic and should not be fully selfish. It should protect long-term individual survival.

---

### 7.2 Social Welfare Objective

The social-welfare objective should represent a society-aware agent.

Expected behavior:

```text
scarcity high → gather
food price high → gather
dead_total high → gather
total_food low → gather
society stable + food safe → work allowed
```

This policy should generally reduce population collapse, food price spikes, and inequality.

It should not blindly gather in every state. A stable society can allow work.

---

### 7.3 Wealth-Maximizing / Self-Interested Objective

The wealth-maximizing objective should represent a selfish but rational economic agent.

Expected behavior:

```text
food critical → gather
food safe → work
coin low + food safe → work
wealth opportunity → work
society scarcity alone does not force gather unless personal survival risk is high
```

This policy should remain self-interested.

It should not become a social-welfare policy.

However, it should also not be suicidal. The agent should gather when its own survival is at risk.

The target behavior is:

```text
selfish but not suicidal
```

## 8. Expected Outcomes

The fine-tuned policies should be compared against zero-shot and few-shot policies.

Expected behavior:

| Policy | Expected Outcome |
|---|---|
| `llm_survival_finetuned` | Stable survival-oriented behavior, similar to or better than few-shot survival. |
| `llm_social_welfare_finetuned` | Scarcity-sensitive gather behavior and lower food prices. |
| `llm_wealth_maximizing_finetuned` | Self-interested behavior with higher prices than social welfare, but without total collapse. |

The ideal result is not that every policy becomes good.

The ideal result is that each objective remains behaviorally distinct while avoiding obviously broken behavior.

Because the adapters are separate, success will be judged by the best checkpoint for each behavior regime, not by a single shared training epoch. This is important because the regimes may learn or overfit at different speeds.

## 10. Dataset Validation

Before training, the dataset must be validated.

Validation checks:

```text
number of examples per behavior regime
gather/work ratio per behavior regime
source distribution per behavior regime
teacher_guided acceptance/rejection ratio
conflicting labels for the same regime/state pattern
whether social_welfare is gather-heavy under scarcity
whether wealth_maximizing is work-heavy but has survival guardrails
whether survival is balanced
```

A dataset report should be written to:

```text
analysis/finetune_dataset_report.md
```

## 12. Risks and Fallbacks

### Risk 1: LoRA training is too slow or unstable

Fallback:

```text
Keep fine-tuning as a documented extension.
Use the completed zero-shot and few-shot comparison as the main project result.
```

### Risk 2: Fine-tuned model produces worse decisions than few-shot

Fallback:

```text
Report this honestly as a negative result.
Fine-tuning does not automatically improve behavioral control.
```

This would still be academically useful.

### Risk 3: Dataset is too rule-like

Fallback:

```text
Add more handcrafted and few-shot-guided examples.
Report dataset source distribution clearly.
```

### Risk 4: Wealth-maximizing becomes too cooperative

Fallback:

```text
Adjust wealth labels so the policy remains self-interested when personal survival is safe.
```

### Risk 5: Separate adapters are harder to manage

Fallback:

```text
Use a single objective-conditioned adapter as a simplified fallback.
```

Separate adapters are the primary plan because they provide cleaner behavior separation, but a single shared adapter remains a valid fallback if training or routing becomes too complex.

### Risk 6: Teacher model labels drift from the intended regime

Fallback:

```text
Filter teacher-guided examples using deterministic regime validators.
Reject or relabel examples that violate the intended behavior regime.
```

Teacher-guided examples are useful for adding nuance, but the teacher model should not redefine the economic objective. The project-defined regime rules remain the source of truth.
---

## 13. Success Criteria

The fine-tuning phase is successful if:

```text
fine-tuned policies run inside the existing simulation loop
fine-tuned policies return valid gather/work actions
fine-tuned policies remain behaviorally distinct
fine-tuned wealth policy avoids zero-shot collapse
fine-tuned social welfare policy improves or preserves society-level stability
fine-tuned survival policy remains balanced
```

The fine-tuning phase does not need to beat every baseline on every metric.

The goal is to test whether training can internalize controllable economic behavior norms.
